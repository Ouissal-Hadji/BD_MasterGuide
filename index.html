Chapter 1 · DB & DBMS

Database Genesis & Database Management System — the why and what

نشأة قواعد البيانات ونظام إدارتها — السبب والتعريف

Why databases? Problems with traditional file systemsلماذا قواعد البيانات؟ مشاكل الملفات التقليدية

🔁 Redundancy
Same data repeated in multiple files → inconsistency & maintenance cost.البيانات مكررة في ملفات متعددة → تعارض البيانات وصعوبة الصيانة.
⚠️ Inconsistency
Semantic links not automatically maintained between files.الروابط الدلالية غير محفوظة تلقائياً بين الملفات.
🔒 Security Issues
Hard to protect multiple copies; recovery is complex.حماية نسخ متعددة صعبة؛ الاسترداد معقد.
🚫 Sharing Issues
No real mechanism for simultaneous multi-user access.لا آلية حقيقية للوصول المتزامن لمستخدمين متعددين.
🔧 Maintenance
Structural changes force rewriting all application programs.التعديلات الهيكلية تجبر على إعادة كتابة جميع البرامج.
🚪 Access
Only programmed operations possible; no interactive querying.فقط العمليات المبرمجة مسبقاً ممكنة، لا استعلام تفاعلي.

Solution: DBMS & Databaseالحل: DBMS وقاعدة البيانات

Database (DB): An organized, electronically stored collection of data designed for easy access, management, and updating. All company information in one place. قاعدة البيانات: مجموعة منظمة من البيانات المخزنة إلكترونياً، مصممة للوصول والإدارة السهلين. جميع معلومات الشركة في مكان واحد.

DBMS: Software that allows interaction with a DB — defining, building, and manipulating data. نظام إدارة قاعدة البيانات: برنامج يتيح التفاعل مع قاعدة البيانات — تعريفها، بناؤها، والتلاعب بالبيانات.

ANSI/SPARC Architecture — 3 Levels of Abstractionمعمارية ANSI/SPARC — 3 مستويات من التجريد

External Level
Individual user/app views. Multiple views can exist. Hides unnecessary detail.المنظور الخاص بكل مستخدم أو تطبيق. قد تتعدد المناظير.
Conceptual Level
Unified view of entire DB. Defines what info is stored and relationships.المنظور الكلي لقاعدة البيانات. يحدد ما يُخزّن والعلاقات.
Physical Level
How data is physically stored on hardware. Hidden from users.طريقة تخزين البيانات على الجهاز. مخفية عن المستخدمين.

DBMS Objectives (8 key points)أهداف DBMS (8 نقاط أساسية)

  1. Provide different levels of abstractionتوفير مستويات مختلفة من التجريد
  2. Ensure physical data independenceضمان استقلالية البيانات الفيزيائية
  3. Ensure logical data independenceضمان استقلالية البيانات المنطقية
  4. Control data redundancyالتحكم في تكرار البيانات
  5. Ensure data integrityضمان سلامة البيانات
  6. Ensure data securityضمان أمن البيانات
  7. Ensure data sharingضمان مشاركة البيانات
  8. Optimize data accessتحسين الوصول إلى البيانات

Integrity Constraintsقيود النزاهة

a. Domain Constraint
Values must be valid & within specified domain.
Ex: Age > 0 AND Age < 150القيم يجب أن تكون ضمن النطاق المحدد.

b. Entity Integrity
PK must be UNIQUE and NOT NULL — ever.المفتاح الأساسي يجب أن يكون فريداً وغير فارغ دائماً.
c. Referential Integrity
FK must reference an existing PK in other table, or be NULL.
"A foreign key must match an existing primary key or be null."المفتاح الخارجي يجب أن يُشير لمفتاح أساسي موجود، أو يكون فارغاً.
d. User-defined

Detailed Operator Examplesأمثلة مفصلة على العمليات

DB used: Students(StudentID, Name, Age, Major) | Courses(CourseID, CourseName, Credits, Price) | Enrollments(StudentID, CourseID, Grade)قاعدة البيانات المستخدمة: Students | Courses | Enrollments

1. Projection + Selection (most common exam pattern)

Relational Algebra
-- Names of students who got grade A
R1 = Enrollments [grade = 'A']
R2 = R1 [studentId]
R3 = R2 [studentId] Students -- Join
RES = R3 [name]

2. Division — "for ALL" pattern

Relational Algebra
-- Students enrolled in ALL courses of 2024
R1 = Project [start_date >= '2024-01-01' AND end_date <= '2024-12-31']
R2 = R1 [proj_num]
RES = Working ÷ R2

3. Self-join — same time comparison

Relational Algebra
-- Projects starting same time as 'bentalleb school renovation'
R1 = Project [title = 'bentalleb school renovation']
R2 = R1 [start_date]
R2' = R1 [proj_num]
R3 = R2 [R2.start_date = Project.start_date] Project
RES = R3 [proj_num] − R2' -- exclude bentalleb itself

4. Intersection — "AND condition across two queries"

Relational Algebra
-- Projects where Tafer Ali worked AND managed by Zademi Asma
R1 = Employee [name = 'zademi asma'] → R2 = R1[emp_id=manager] Project → R3 = R2[proj_num]
R4 = Employee [name = 'tafer ali'] → R5 = R4[emp_id] Working → R6 = R5[proj_num]
RES = R3 ∩ R6
✅ Key pattern to memorize: When asked "projects NOT managed by X" → difference. When "employees who worked on ALL projects" → division. When "managers who are NOT engineers" → difference between managers set and engineers set.النمط الأساسي للحفظ: "المشاريع التي لم يديرها X" → فرق. "الموظفون الذين عملوا في جميع المشاريع" → قسمة.

Method 1: WHERE (Cartesian Product)
SELECT name
FROM employees E, working W, project P
WHERE E.emp_id = W.emp_id
  AND W.proj_num = P.proj_num
  AND qualification = 'engineer'
  AND title = 'National road RN15';
Method 2: INNER JOIN
SELECT name
FROM employees E
INNER JOIN working W ON E.emp_id = W.emp_id
INNER JOIN project P ON W.proj_num = P.proj_num
WHERE qualification = 'engineer' AND title = 'National road RN15';
Method 3: Nested Subquery
SELECT name FROM employees
WHERE emp_id IN (
  SELECT emp_id FROM working
  WHERE proj_num IN (
    SELECT proj_num FROM project
    WHERE title = 'National road RN15'))
AND qualification = 'engineer';
Method 1: NOT EXISTS (most common in exams)
-- Employees who worked on ALL 2024 projects
SELECT name FROM employee E
WHERE NOT EXISTS (
  SELECT proj_num FROM project
  WHERE start_date >= '2024-01-01'
    AND end_date <= '2024-12-31'
    AND proj_num NOT IN (
      SELECT proj_num FROM working
      WHERE emp_id = E.emp_id));
Method 2: GROUP BY + COUNT
-- Employees enrolled in ALL courses
SELECT studentid
FROM enrollment
GROUP BY studentid
HAVING COUNT(courseid) = (
  SELECT COUNT(DISTINCT courseid)
  FROM enrollment);
Aggregate Functions
-- COUNT, SUM, AVG, MIN, MAX
SELECT location, AVG(cost)
FROM project
GROUP BY location
HAVING AVG(cost) >= (SELECT AVG(cost) FROM project);

-- Managers with total employees supervised
SELECT name, COUNT(W.emp_id)
FROM Employee, Project P, Working W
WHERE emp_id = manager
  AND P.proj_num = W.proj_num
GROUP BY manager;

Chapter 5 · Normalization

Functional Dependencies, Normal Forms, Synthesis Algorithm

التبعيات الوظيفية، الأشكال الطبيعية، خوارزمية التركيب

Why Normalize?لماذا نُطبّع؟

A bad schema (universal relation) causes 3 anomalies: المخطط السيئ (العلاقة الكونية) يسبب 3 حالات شاذة:
Update anomaly: Same info must be changed in multiple rows.نفس المعلومة يجب تغييرها في صفوف متعددة.
Insert anomaly: Can't add new entity without related data.لا يمكن إضافة كيان جديد بدون بيانات مرتبطة.
Delete anomaly: Deleting last reference loses all info about entity.حذف آخر مرجع يُفقد جميع معلومات الكيان.

Functional Dependencies (FD)التبعيات الوظيفية

X → Y    means: knowing X uniquely determines Y
Elementary FD:
X → Y is elementary when:
• Y is single attribute ∉ X
• No proper subset of X determines Y

Ex: teach_id → name ✓
teach_id, name → phone ✗ (name not needed)
التبعية الوظيفية الأولية:
• Y سمة واحدة لا تنتمي لـ X
• لا توجد مجموعة فرعية من X تحدد Y

مثال: teach_id → name ✓
Direct FD:
X → Y is direct when:
• No Z exists such that X → Z AND Z → Y
(no transitive chain)

Ex: student_id → classroom is NOT direct if
student_id → group → classroom
التبعية الوظيفية المباشرة:
• لا يوجد Z بحيث X→Z و Z→Y
(لا سلسلة انتقالية)

FD Properties (Redundancy Types)خصائص التبعية (أنواع التكرار)

🎯 Exam favorite! Identify redundancy type for each FD.من أكثر ما يأتي في الامتحان! تحديد نوع التكرار لكل تبعية وظيفية.
PropertyRuleالقاعدةExampleمثال
ReflexivityY ⊆ X → X → YW,T → T  ✓ reflexivity
AugmentationX → Y ⟹ X,Z → Y (adding Z is redundant)X,W→S and X,W,T→S: T is augmentation
TransitivityX→Y and Y→Z ⟹ X→Z (redundant)Z→Y and Y→T ⟹ Z→T redundant
Pseudo-transitivityX→Y and Y,W→Z ⟹ X,W→ZZ→X and X,W→V ⟹ Z,W→V redundant

Normal Forms — The 3 Levelsالأشكال الطبيعية — المستويات الثلاثة

1NF
First Normal Formالشكل الطبيعي الأول
All attributes are atomic (indivisible) and single-valued.
❌ Fails: color = "black AND red" (multivalued) OR address includes city (not atomic) جميع السمات ذرية (غير قابلة للتقسيم) وأحادية القيمة.
❌ فشل: اللون = "أسود وأحمر" (متعدد القيم)
2NF
Second Normal Formالشكل الطبيعي الثاني
In 1NF + every non-key attribute fully depends on the entire primary key (no partial dependency).
❌ Fails: R(A,B,C,D) key=(A,B) and A→D exists → D partially depends on key في 1NF + كل سمة غير مفتاحية تعتمد على المفتاح الأساسي كله (لا اعتماد جزئي).
3NF
Third Normal Formالشكل الطبيعي الثالث
In 2NF + no transitive dependency (no non-key attribute determines another non-key attribute).
❌ Fails: Employee(empid, name, daira, wilaya) — daira→wilaya transitive! في 2NF + لا توجد تبعية متعدية (لا سمة غير مفتاحية تُحدد سمة أخرى غير مفتاحية).

Synthesis Algorithm (Decompose to 3NF)خوارزمية التركيب (التحليل إلى 3NF)

🎯 This IS the exam exercise 3! ~6 points. Master it.هذا هو تمرين 3 في الامتحان! ~6 نقاط. أتقنه.
Steps:الخطوات:
  1. Start from the minimal FD cover (elementary + direct FDs only)ابدأ من الغطاء الأدنى للتبعيات (الأولية والمباشرة فقط)
  2. Create a separate relation for each isolated attribute (not determined by anything) → it becomes its own key R0أنشئ علاقة لكل سمة معزولة (لا يحددها شيء)
  3. Identify the largest set X that determines attributes → Create R(X, A1, A2...) with X as keyحدد أكبر مجموعة X تُحدد سمات → أنشئ R(X, A1, A2...)
  4. Remove those FDs from the coverأزل تلك التبعيات من الغطاء
  5. Repeat until FD cover is emptyكرر حتى يصبح الغطاء فارغاً

Exam Example (from corrigé)

Given UR and FDs
UR(pat_id, pat_name, birthdate, room_num, type, beds-nbr, doctor_id, doc_name, doc_phone, qualification)

FDs:
  pat_num → pat_name, birthdate, room_num
  room_num → type, beds-nbr, doctor_id
  doctor_id → doc_name, doc_phone, qualification

Key = pat_num  (pat_id is isolated!)

Synthesis Result:
R0 (pat_id)                                          ← isolated
R1 (pat_num, pat_name, birthdate, room_num)          ← pk: pat_num
R2 (room_num, type, beds-nbr, doctor_id)             ← pk: room_num
R3 (doctor_id, doc_name, doc_phone, qualification)   ← pk: doctor_id

Q1 · Conceptual (0.5pt each) 2 pts

For each statement, indicate TRUE or FALSE with justification:لكل عبارة، حدد صحيح أو خاطئ مع التبرير:

a) Every relation in a DBMS must have a foreign key.
b) In relational algebra, all operators directly supported by SQL.
c) In SQL, there are no duplicate tuples by default.
d) A primary key is fundamentally a candidate key.

a) FALSE — A relation must have a PK, but a FK is only needed when referencing another table.
b) FALSE — Division (÷) has no direct SQL operator; implemented via NOT EXISTS or GROUP BY+COUNT.
c) FALSE — SQL keeps duplicates by default (ALL). Use DISTINCT to remove them.
d) TRUE — A PK is chosen from among the candidate keys. It IS a candidate key by definition.
Q2 · E/R & Relational Schema (3 pts) 3 pts

Consider a university database. The business rules are:
• A student belongs to exactly one group. A group has multiple students.
• A student can enroll in multiple courses. A course has multiple enrolled students. The enrollment date is recorded.
• Each course is taught by one professor. A professor can teach multiple courses.

1) (1pt) List the cardinalities for each relationship above.

Q4 · FD Analysis (2 pts) 2 pts

Given RU(X, Y, Z, S, T, V, W) and DF = {Z→X,Y ; Y→T ; X,W→V,S}

For each FD below, identify if it presents redundancy and explain which property:
a) Z → T
b) X,W,T → S
c) Z,W → V
d) W,T → T بالنظر إلى التبعيات الوظيفية المعطاة:
لكل تبعية، حدد إن كانت تحتوي على تكرار واذكر نوع الخاصية:

a) Z → T: Redundancy by TRANSITIVITY — Z→Y and Y→T, therefore Z→T is derived.

b) X,W,T → S: Redundancy by AUGMENTATION — X,W→S already exists; adding T is unnecessary (augmentation).

c) Z,W → V: Redundancy by PSEUDO-TRANSITIVITY — Z→X and X,W→V, therefore Z,W→V is derived.

d) W,T → T: Redundancy by REFLEXIVITY — T is a subset of {W,T}, so W,T→T is always trivially true.

SQL Q3 (1.5pt)1.5 pts

List the names of employees who worked on ALL projects managed by manager with ID = 5.أسماء الموظفين الذين عملوا في جميع المشاريع التي يديرها المدير رقم 5.

-- Method 1: NOT EXISTS (division)
SELECT name FROM employee E
WHERE NOT EXISTS (
  SELECT proj_num FROM project
  WHERE manager = 5
    AND proj_num NOT IN (
      SELECT proj_num FROM working
      WHERE emp_id = E.emp_id));

-- Method 2: GROUP BY + COUNT
SELECT E.name
FROM employee E, working W, project P
WHERE E.emp_id = W.emp_id
  AND W.proj_num = P.proj_num
  AND P.manager = 5
GROUP BY E.emp_id, E.name
HAVING COUNT(DISTINCT W.proj_num) = (
  SELECT COUNT(*) FROM project WHERE manager = 5);

Consider the universal relation for a hospital admissions system:

UR(pat_id, pat_name, pat_phone, ward_id, ward_name, capacity, nurse_id, nurse_name, admission_date, diagnosis)

Validated FDs:
• pat_id → pat_name, pat_phone, ward_id, admission_date, diagnosis
• ward_id → ward_name, capacity, nurse_id
• nurse_id → nurse_name

1) (0.5pt) What is UR's key?
2) (1pt) What is UR's normal form? Justify each level.
3) (2pts) Apply the synthesis algorithm to produce the 3NF schema. Show the minimal FD cover and steps.
4) (0.5pt) If a patient can have multiple diagnoses, which normal form is affected and why?
5) (1pt) Write new FDs if: "a nurse is responsible for a ward during a specific shift (day/night)" and "a ward can have multiple nurses". علاقة كونية لنظام إدخال مستشفى:
UR(pat_id, pat_name, pat_phone, ward_id, ward_name, capacity, nurse_id, nurse_name, admission_date, diagnosis)

التبعيات المعتمدة كما هو مذكور أعلاه.

1) ما هو مفتاح UR؟
2) ما هو الشكل الطبيعي لـ UR؟ برّر كل مستوى.
3) طبّق خوارزمية التركيب للحصول على مخطط 3NF. أظهر الغطاء الأدنى والخطوات.
4) إذا كان للمريض تشخيصات متعددة، أي شكل طبيعي يتأثر ولماذا؟
5) اكتب تبعيات وظيفية جديدة للقواعد المذكورة.

1) Key = pat_id — pat_id determines all other attributes directly or transitively.

2) Normal Form:
• 1NF? YES — all attributes are atomic and single-valued (assuming diagnosis is a single value).
• 2NF? YES — key is a single attribute (pat_id), so no partial dependency possible.
• 3NF? NO — ward_id→ward_name, capacity, nurse_id is a transitive dependency (non-key→non-key). Also nurse_id→nurse_name. UR is in 2NF only.

3) Synthesis Algorithm:
Minimal cover (all FDs are already elementary and direct after checking):
pat_id → pat_name, pat_phone, ward_id, admission_date, diagnosis
ward_id → ward_name, capacity, nurse_id
nurse_id → nurse_name

Result:
R1 (pat_id, pat_name, pat_phone, ward_id, admission_date, diagnosis)  ← pk: pat_id
R2 (ward_id, ward_name, capacity, nurse_id)                           ← pk: ward_id
R3 (nurse_id, nurse_name)                                             ← pk: nurse_id
4) 1NF is affected — if diagnosis can have multiple values, it is no longer atomic/single-valued → violates 1NF. Fix: decompose into a separate DIAGNOSIS(pat_id*, diagnosis) relation.

5) New FDs:
• "Nurse responsible for ward during shift" → (ward_id, shift) → nurse_id
• "Ward can have multiple nurses" → No FD (a ward doesn't determine a unique nurse)
